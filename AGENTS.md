# AGENTS.md — dromas-client

**The verifiable client side of Dromas: the protocol's spec, the Go client and `dromas` command, a client in plain shell on stock `age` and `ssh-keygen`, test vectors, and tests that run the client against a server that forges.** Dromas carries end-to-end encrypted, sender-authenticated messages between bots, built so that nobody has to trust its server: everything a mailbox relies on is checked here, in code you can read and by tests you can run.

🛑 **This repo is public: every push publishes.** Never commit a secret, a private key (the vectors' keys are published test keys: § Tests), a token or an internal hostname, and never copy text from a private note without a decision to publish it.

**Judging whether Dromas is secure → `SECURITY.md`:** each promise a mailbox is given, the spec section with the whole rule, the code and test that hold it, and how to report a vulnerability privately. **Changing it → § Contributing, then § Rules by area for the code you touch.**

## Contributing

### Sign off every commit

Each commit carries your human's sign-off, made with `git commit -s` (the Developer Certificate of Origin: `CONTRIBUTING.md`).
- **It is their certification, not yours.** Tell them the repo requires it. With their say-so you may run `git commit -s` for them: it writes the line from their git identity.
- 🛑 **Never sign as yourself, never write a `Signed-off-by:` line by hand, and never put anyone else's name on one.**
- **Name yourself** in an `Assisted-by:` or `Co-Authored-By:` trailer.
- A pull request whose commits lack the line fails the DCO check and is not merged. `CONTRIBUTING.md` has the commands that add it to commits already made.

### Where things are written

- **`PROTOCOL.md` is the spec, written as an RFC is:** numbered sections, each rule once in BCP 14 capitals, the reasoning only in § 15 Security considerations (the threat model, what a hostile server can and cannot do, the residual risks). It cites a standard rather than restating it, and states only where Dromas differs from it. A change to the wire, a check or a refusal changes it in the same commit as the code. What a command prints, the order of a client's own steps, its retries, its words and its files are the code's, and the spec does not restate them. It describes the server only as a client meets it (what each operation means, its checks and refusals, what it promises to store): never how a server stores things, a setting's value, a person's words, history, issue numbers, a comparison, or what is not yet built. A rule is cited by its section, `PROTOCOL.md §11.10`. Anything undecided or unbuilt is an issue; every open issue is wanted for v1, and one whose outcome could change the wire is settled before the freeze.
- **`api/openapi.yaml` is normative for the HTTP shapes, in OpenAPI 3.1, and no server serves it:** routes, methods, members and their types, statuses, codes and headers are stated there and nowhere else, and its descriptions say what an item is and point at the section that gives its meaning. A change to a shape changes it in the same commit. `api/`'s tests hold it to `protocol/`'s codes and members, and `api/apitest` holds a server's answers to it: the fake server here, and every test server in dromas-server. It carries no byte format and no check: those are `PROTOCOL.md`'s and the vectors'.
- **`PRECEDENTS.md` is the one place a comparison with another system is kept:** Part 1 sets Dromas beside whole systems, Part 2 each decision beside the system or standard that does the same, and Part 3 the reference server's own build choices. A row is added the day a big decision on the wire or in the security model is made; a client's own behaviour gets none. A row is the decision, its precedents and where ours differs and why: never how it was decided, the spec restated, or a standard explained to a reader who knows it. Every claim about another system says how it is known: `read <date>` with its source, `review 2026-10-10`, or `from memory`, never a number from memory as if read. `PROTOCOL.md` points at it once, from its introduction, and carries no comparison; grow no second table anywhere.
- **Every page and comment says what holds now, never how it came to be:** no story of a change, a finding or a mistake, no "was", "since" or "once" of this project's own past, and no date but one that says when a source was `read`, a measurement was `measured`, a review was made (`review`) or an outside document is `dated`; `PRECEDENTS.md` dates its claims by its own rule above. Why a rule holds is said in the present tense; how it came about is its pull request's and its commit's. `TestEveryPageSaysWhatHoldsNow` fails on any other date in a page, a comment or a workflow.
- **No judgement is written as a fact,** on any page, in a comment or in an issue: write what was measured, read at a source or decided. Nothing ranks one cipher, key type or design over another without the source that says so, and a comparison's source is in `PRECEDENTS.md`.
- **The README says as little as it can:** what an agent must know to run a mailbox safely, each command once, and pointers. Before adding a line, find one to cut.
  - Two lines are the maintainer's: the status line's freeze date, which moves only on his word, and the line that sends a reader to the open issues.
  - Where the README or the spec states a limit that an open issue plans to change, the issue's number sits beside it: agents judging the service from its pages read a limit with no number as permanent.
  - The status line never lists the operator as a limit. Who terminates TLS for dromas.dev is said once, in § No Server Trust.
  - Three tests hold its command lines: `TestHelpAndREADMENameTheEchoMailbox` here, one in dromas-server for the command its link page gives, and one kept with dromas.dev's site for every command in its `llms.txt`. Change a command line in each place that gives it.
- **`SECURITY.md` is the one place for how to report a vulnerability and for each security claim beside what holds it.** A new claim, or a change to what holds one, edits its row in the same commit; a claim goes there only with the test or code that holds it, and what is not tested is said there too. Elsewhere, point there: the threat model and what a server sees and can do are `PROTOCOL.md` §15.
- **A behaviour is described once, beside the code that does it:** in its doc comment, or the command's help, and held by a test. Nothing here or in the README restates it. A rule in this file is a rule, with the code that keeps it named; a sentence that only says what a function does is that function's doc comment.
- **Layout:** the repo's is `README.md` § What is here; a mailbox's files are at the top of `client/doc.go`.

### How a design is chosen

- **Priorities, in this order:** the correct encryption; then a server that is feasible and fast, not as cheap as possible; then simple things simple for the user.
- **Before the protocol freeze, a fix is chosen for being correct:** backwards compatibility and leaving the wire unchanged carry no weight, in a design, an issue or a recommendation.
  - 🛑 **Nor does a rule, format or behaviour of our own** (the server's, the spec's, a client's files or the script's): one that forces a workaround is a design question, put to the maintainer with the best design for every side and its cost, and every side changes to the answer together. It hides as a command changing shape, a workaround for the other side's rule, a known variance, or a reason that names what is already written (#126 audits for it).
  - **Nor does an old tool:** the design assumes a current client and a modern library. What the oldest `ssh-keygen` or `age` can do is never a reason for or against a design; the script's floor follows the design.
- **A design follows industry practice, read at its source** (an RFC, a major system's documentation, then its code), never this project's own earlier choice. Where a standard has a reference implementation, its behaviour is the practice: OpenSSH for SSHSIG and certificates, age for age. Where Let's Encrypt meets the same concern as a free public API anyone may call (limits, renewal, revocation, abuse), its practice is the precedent (`PRECEDENTS.md`, Part 2, § 4). A statement of the design that differs is challenged, whoever made it. **A deviation is justified as part of the design,** its reason in `PRECEDENTS.md` beside the systems it differs from; one with no reason there is a defect.
- 🛑 **A format takes a layout others already use, and its overhead is a fixed number of bytes, never a share of the message.** Read what the standards do, and what went wrong with them, before choosing a layout, and give each option's cost beside it. Every format that cannot change after the freeze gets that look once (#39).
- **A list of entries of like, bounded size is bounded by a count, never by bytes** (an ACL's `protocol.MaxACLEntries`, #440): a count is the easier rule to read and to follow. One bound, set well past any real use, so its edge never needs revisiting.
- **A speed call is made among standard tools and norms:** never replace a standard function with hand-written code to save CPU, and leave deeper optimisation until real load can be measured.
- **Clocks: every check is exact at the clock of whoever makes it, and whoever makes a time-limited thing leaves `protocol.MaxSkew`, an hour, of room, but for a client's renewal of a prekey shorter than a day, which leaves five minutes** (`margin`, `shortRoom`; `PROTOCOL.md` §3.4; `PRECEDENTS.md` § Clocks; decided on #40 and #575). 🛑 Add no allowance to a check, and never make a thing that asks for exactly what its verifier takes: a certificate starts an hour before it is made, a server takes a prekey up to an hour past what a client asks for, a reader takes a `sent_at` up to an hour ahead. The room covers the maker's own calls too, beside it: two minutes for a post in the server's keep of messages (`protocol.PostTime`), and for a renewal an hour at a prekey lifetime of a day or more, five minutes below (`renewTime`). Exactness to the second is for what is cryptographic, not for how long a server holds a message.
  - 🛑 **A test of anything timed uses two clocks:** with one, no test can see that a mailbox two seconds fast cannot register (`client/clock_test.go` is the pattern).
  - 🛑 **A test that races a bound in time (a stall, a drain's time, a lock's patience) runs in a `testing/synctest` bubble, on fake time, against `fakeserver.NewInMemory`** (`httptest.NewTestServer`'s in-memory network; `client.Bounded` gives a mailbox the default client's bounds): on real time, a busy runner's stall reads as the code's (#477, #482).
  - A client reports how far its clock is from a server's, as the server's word, and never adopts it or tells its reader to. An outbox entry dated ahead of the clock is held at every attempt, by the reading that dates the post, once the recipient's mailbox is read (`seal`; #334). 🛑 A key that a message may be waiting for is never deleted to recover from a wrong clock: a mailbox cannot know a statement was never published.

### Tests

- **Every client passes `testdata/vectors/`,** and the shell client is tested the way agents run shell: a fresh shell per command.
- **`client/`, `cmd/dromas` and `sh/` are tested against `internal/fakeserver`:** an honest in-memory server that a test turns hostile with a middleware, the common forgeries `internal/forge`'s (`README.md` § Tests). The forging-operator tests live here, so anyone can run the checks they are told to verify. The fake checks little by design: a test of what the real server enforces belongs in dromas-server.
- **`client/testdata/statetable.golden` is what each command does in each state of a mailbox** (`TestStateTable`): its directory whole or its identity alone, what its server holds of it and of its revocations, with the server answering, refusing or silent; each cell's line is what the command returned, every call it made and what changed in the mailbox. A change to what a command does shows there: `go test ./client -run TestStateTable -update` writes the file again, and each changed line is read before it is committed.
- **`sh/` is tested by `go test ./sh`:** the script against the fake, a fresh shell per command, each test on a world of its own (`sh/world_test.go`), its verdicts on the vectors it answers to (§ The shell client) against the Go client's, and a script mailbox and a Go mailbox exchanging messages. A test skips, naming the tool, when one is missing; age is built, never missing (below), and the package fails if `go tool` cannot build it.
  - 🛑 **Run it with `-count=1`:** bash reads `sh/dromas.sh`, which Go's test cache does not see, so after an edit to it `go test ./sh` prints `ok … (cached)`, the result from before the edit.
  - **Where the local age makes no post-quantum keys, the tests take the age `go.mod` names as a tool,** at the version the client links (`internal/agetool`, `go tool -n age`): the script's tests, the vectors' and dromas-server's `test/interop.sh` run on any machine with Go.
  - To hold the script to another OpenSSH, build its release (`./configure [--without-openssl] && make ssh ssh-keygen`) and put it first in `PATH`: `go test -count=1 ./sh -v` names the build and each known variance it met (`PROTOCOL.md` Appendix A).
- **Vectors:** `testdata/vectors/generate.sh` uses stock tools only (age ≥ 1.3 just for the two ciphertexts, which it keeps). A re-run must change nothing but what you meant to change: diff the tree. 🛑 **Its keys are PUBLISHED test keys,** RFC 8032's for every Ed25519 key, RFC 6979 §A.2.5's for mailbox C's P-256 identity, and C2SP's age testkit's hybrid identity for B's and C's prekey: never put any other private key in this repo. A certificate is made once and kept, since a second run cannot make the same bytes.
- **A command killed at each step at which it writes the mailbox leaves it whole** (`client/crash_test.go`): a copy of the test binary runs the command and kills itself with SIGKILL at the step (`steps.go`), and the next commands find nothing lost and nothing twice. `TestStepsAreTheCode` holds the list of steps to the `step` calls: a new write that something follows gets a `step` call and its place in `steps`.
- **What a reader runs on bytes before a signature verifies has a fuzz target, seeded from the vectors** (`protocol/fuzz_test.go`, `FuzzParsePass`, `FuzzIfNoneMatch`, `sshsig`'s two), each holding the code to its doc comment: no panic, a refusal an error with no result beside it. A new parser of unsigned bytes gets one. Run each alone in its own package, `go test -run '^$' -fuzz '^FuzzX$' -fuzztime 2m -parallel 1 ./protocol` (`./sshsig` for `sshsig`'s two: in the wrong package a target fuzzes nothing and still passes), and keep a crash's input as a seed.
- 🛑 **A claim about every member of a set is held by a test that builds the set from the code, never by a list typed by hand:** a typed list holds the members its writer thought of, and the next one passes untried (#406, #408, #414). `TestEveryLockingCommandIsTriedFinished`, `TestStepsAreTheCode` and `TestEveryEntryThatWaitsIsTriedWithItsContext` read theirs from the source, `TestEveryRefusalOfThePassIsTriedUnderANewOne` and `TestNoAnswerProvedIsUndeliverable` from the values the code uses, and dromas-server's `TestEveryRequestIsCountedBeforeAnythingIsDone` from its routes.
- 🛑 **A test holds only what the code promises:** an order, a time or a count that the code does not give is never asserted, and one green run of a check that depends on timing proves nothing. A list ordered by files' times does not give recv's order: two files kept within one tick of Windows' clock share a time. Hold what the doc comment says (`TestLinesNameAPeerByItsAliasAndInboxListsWhatItKeeps`: the same lines, oldest first by `sent_at`), and where two outcomes are both right, take either (`TestAMessageFromASenderNotAllowedIsHeld`'s two orders of what `peer allow` moves).
- **Tests run in parallel** (`t.Parallel()`), but one that sets a package's state (`client.SetStep`, `SetWriteFault`, `SetLockPatience`, `SetRequestTimeout`, `SetDrainLimits`) or the process's (`t.Setenv`) runs alone, as does one that needs a port to stay free (`sh/`'s `TestAServerThatIsNotThereIsNoAnswer`) (#427). **A test of 5 s or more skips under `-short`**, saying so (`if testing.Short()`); CI never passes `-short`. **The tests build with `-tags dromas_nofsync`** (`scripts/check.sh`), which leaves out every flush to the disk (`client/fsync.go`): a test kills a process, never the machine.
- **No mutation pass:** do not add one unasked.

### Before and after every push

- **Before:** `scripts/check.sh push`: gofmt, vet, every test with the skip check and the race test (`full`, what CI's test job runs), then `golangci-lint run ./...` (`.golangci.yml`, which dromas-server shares: its linters, every finding shown, and none from `_test.go`) and govulncheck at the version the script pins. While working, `scripts/check.sh` alone: vet and the tests `-short` keeps, in well under a minute. On macOS the script leaves `./sh` to CI (its header says why). `go test` cross-tests against `ssh-keygen`, and skips that where it is missing. **CI runs `scripts/check.sh full` on every push to `main`, every pull request and every merge group** (`.github/workflows/ci.yml`), on Ubuntu with two OpenSSH releases and on arm64, on macOS on Apple silicon, on Windows on x64 and arm64, and on FreeBSD and OpenBSD in VMs (`./sh` left out on macOS, Windows and the BSDs), and on macOS on Intel, NetBSD and DragonFly in the daily run alone (`release.yml` runs the rest of `ci.yml` again, without them: the Intel runner compiles from a cold cache at a third of the others' speed, NetBSD's VM at a third, DragonFly's at a quarter): each system and architecture a release is built for, the Intel Mac's tested on `main` once a day rather than at each commit or release, where a test that skips for a missing tool fails the job, each fuzz target for an hour once a week (never on a push), and dromas-server's `scripts/check.sh full` against the commit through a `go.work` (that repo requires a release of this one).
- **After: `needs-audit`, for a change that needs a second reader, never by default.** A change to what a client or the server checks, signs, keys, times or deletes, that its tests and their controls do not show right by themselves, and that nobody else read as it shipped (or what was written after its review has not been read), gets a new issue labelled `needs-audit` in the client repo, whichever repo changed. A change its tests hold, one to the shell client alone (the proof piece, § The shell client), and one to docs, wording or tests get none. The issue it fixes closes as usual. 🛑 **The issue is the auditor's whole brief:** the commits, the claims to try to break, where to look first, what is known and open, how to run it, and what closes it, so an outside agent with no other context can work from it. Nothing waits on one: it is not a gate. Whoever audits closes it, saying what was read, run and tried, and files what it found as ONE issue in this repo, `findings: the audit of #N`, whichever repo each is in: each finding a numbered item, with its severity (Low, Medium or High), its kind (a defect, a claim no test holds, or stale words) and how to reproduce it. A finding of Medium or above, or one that breaks a `SECURITY.md` claim or the wire (`PROTOCOL.md`), is also an issue of its own, in the repo of its code, named at its item. A fix names its item (`#M item 2`), and the findings issue closes once each item is fixed or declined. #45 is the pattern of a brief.

### Releases

- **A release is a tag `v0.<minor>.<patch>` signed by a key in `.github/allowed_signers`, made by `task release` (`Taskfile.yml`, GoReleaser's own release task):** `svu` names the next patch (`BUMP=minor` a new minor), Task shows it and asks, and refuses a checkout off `main`, dirty, behind `origin/main`, already released, or with no hand-run of `release.yml` passed on that commit (`gh workflow run release.yml --ref main`: every build and test a tag runs, so a tag is never the first run of any); then `git tag -s` and the push (`NOTES=<file>`: the tag's message, whose body heads the release's notes). **`.github/workflows/release.yml` does the rest:** `git verify-tag` against `allowed_signers` (a lightweight, unsigned or unnamed tag fails it), all of `ci.yml` on the tagged commit, GoReleaser (`.goreleaser.yaml`: archives, SBOMs, `checksums.txt` signed with cosign, every file attested), then the published release checked as README § Install has a user check it and built again from its tag, each archive compared. 🛑 **Every step is a tool's own documented feature or a named peer's practice, and the workflow's comments say whose; nothing in the chain is hand-written where a standard path exists.** No tag is `v1.0.0` or above, the protocol freeze included, until the maintainer decides one is. A dependency moves in a commit before the tag (§ Every client), never in the release.
- **A release tag is signed with the maintainer's key, and only he can unlock it:** its passphrase is his alone, and it is in no `ssh-agent` until he loads it for a release (`task release` refuses while it is locked). Custos, his AI assistant, runs `task release` only on his go for that release and once he has unlocked the key; this human gate is the point (§ The maintainer's own commits); adding a key to `allowed_signers` is his commit. A patch or a new minor is released on his word. A platform joins `.goreleaser.yaml` once CI runs the client on it: the BSDs are next.

## Rules by area

Each rule names the code that keeps it and, where one exists, the test that holds it. 🛑 marks a trap someone has fallen into.

### Every client

- **Verification always on, with no flag to skip it. Fail closed. Message bodies are untrusted data. Where a mailbox's parts are is its config file's (`cmd/dromas/config.go`; `client.Layout`), and neither is ever found from the working directory. What the client makes is 0700 (on Windows, which has no modes, a protected access list of its user, SYSTEM and the Administrators: `private`), and it changes nothing it did not make.**
- **ssh's convention for what a mailbox's owner made:** a private key file others can reach is refused (`checkKeyFile`, ssh(1)), a config file others can write is refused (`CheckConfigFile`, ssh_config(5)), and a directory is not judged. 🛑 **The client writes no `.gitignore` and runs no git** (`KeysInGit` looks for a `.git` above a key and says so): it is someone else's repository, and git executes configuration it finds inside one.
- **The identity is a plain OpenSSH key file,** no seed and no passphrase, so `ssh-keygen` reads it. A mailbox's files are in `client/doc.go`; `aliases` is `<name> <address>` lines, which a person may write, and a name is never moved by the client.
- 🛑 **Prekeys are never derived from a seed, never backed up or synced, never kept where old versions survive (a secrets manager, git, snapshots), and never reused** (`PROTOCOL.md` §12.1): any of those voids the forward secrecy every mailbox has.
- **Every file a mailbox keeps is on disk before anything depends on it:** written beside it, synced, moved into place, and its directory synced (`writeFile`, `makeState` for the state file, which bbolt would make in place, `dr_put`, `dr_putline`, `dr_putout`; decided on #99), and a prekey, its statement and its working key are synced before any upload names them. A crash leaves the old file or the new one, never an empty one, which a mailbox would read as a fault.
- **What the client writes about the mailbox itself is in its `state` file,** a bbolt database, each change one transaction (`client/store.go`): what goes together is written together, and no file's existence stands for a step having finished. Keys, messages and the owner's own files stay files: a key deleted inside a database stays in its free pages, and messages and the owner's files are a person's to read, move and delete. 🛑 **No server call is made inside a transaction.**
- **A mailbox's format is one number in its `state` file** (`client/format.go`; decided on #462): every command refuses a newer one once it has the state file, before anything else of the mailbox but its identity is read or written; a reading refuses an older one; a command that takes the lock brings it forward (`bringForward`), each step safe to run again, the format recorded last. A state file that records none, or no state file at all, is format 1. 🛑 **From the protocol freeze, a change to what a mailbox's files hold, or where they are, is a new format:** a step in `formatSteps` that recognises the old form from the files themselves, and its line in `client/doc.go` (`TestDocNamesEveryFormat`). Before the freeze, format 1 changes in place, with no step and no new number; `TestANewerFormatIsRefusedByEveryEntryWritingNothing` and `TestAnOlderFormatIsBroughtForwardByACommandAndRefusedByAReading` run every entry `waits` holds to the code.
- **The mailbox's lock is its `state` file,** held open by a command from its start to its end: bbolt's flock refuses a second process, which waits, and the kernel lets go of it however its holder ended (`client/lock.go`; #235). The script runs a mailbox of its own, with its own `lock/` (`dr_lock`). `base-dir` on a network filesystem is refused where the system can tell (`networkFilesystem`, #188), and the base directory is never split (`client.Layout`).
  - **Every command that writes the mailbox holds the lock from start to end, and waits while another holds it** (`hold`, `locked`, `dr_lock`; decided on #62, #83 and #96). A new command that writes the mailbox takes it; one that only reads (`Status`) opens the state file read-only, which waits while a command writes (`reading`). Each takes the `Mailbox`'s slot first (`claim`), so goroutines sharing a `Mailbox` take turns as processes do (#329), and its context ends the wait, at every entry that waits (#330; `TestAWaitForTheLockEndsWithItsContext`, `TestAWaitForTheSlotEndsWithItsContext`, whose list `TestEveryEntryThatWaitsIsTriedWithItsContext` holds to the code); a writer that waits holds the mailbox's gate, which every reading takes first, so readings that overlap do not hold it back (#344).
  - 🛑 **A writer takes it at its exported entry and nowhere below:** the lock is not re-entrant, so an exported method that holds it calls the unexported twin of another (`syncACL`, `prune`, `resolve`), never the exported one, which would wait for itself. In the script, a command that another command runs works under its caller's lock (`dr_held`).
- 🛑 **A protocol token compared in any case is lowered by `protocol.LowerASCII`, and by nothing else** (a pass's scheme and names, a range's unit, a host a pass names; #268, #405): Unicode's case folding reads characters that are no token's as ASCII letters (U+017F as `s`, the Kelvin sign as `k`), so `forbidigo` in `.golangci.yml`, which dromas-server shares, refuses `EqualFold`, `ToLower`, `ToUpper` and `ToTitle` of `strings` and `bytes`, which raise as they lower.
- **Dependencies are minimums, never pins, moved to the latest by committed updates:** bump `go.mod` in a commit (`go get -u ./... && go mod tidy`, tests green), never inside a build, so every build matches a commit and `go install …@latest` gets the new versions. Dependabot opens them weekly as pull requests, for the modules and the workflow's actions (`.github/dependabot.yml`), and one is merged once CI passes on it. `go.sum` is checked against the Go checksum database.

### The shell client

- **`sh/dromas.sh` is the proof that a mailbox made of stock `age`, `ssh-keygen`, `curl` and `jq` exchanges messages with a Go mailbox,** and nothing more: not a client to run, and not a second implementation of the Go client. It has `init`, `addr`, `send`, `recv` and `prekey renew`, and the README says to use the Go client. It runs a mailbox of its own, never the Go client's directory: its own variables (`DR_HOME`, `DR_MAILBOX`) and default (`~/.config/dromas-sh/`), and a directory holding the Go client's `state` refused (`dr_ownmailbox`; #331).
- **`testdata/vectors/` is the contract between implementations, and the script answers to the part of it that is the proof:** every crypto and container vector (`a/`, `b/`, `c/`, `identity/`, `cert/`, `sig/`, `prekey/`, `revoke/`, `revoked/`, `plain/`, `message/`), each envelope it must take (`envelope/accept-*`) and each envelope refusal that guards the five (`envelopeFive` in `sh/`), and each server answer the Go client takes, refusing each that breaks a member the script reads (`answerRead`), code for code where it can give the code, and on OpenSSH's builds to their known variances (`PROTOCOL.md` Appendix A). The rest of `json/`, `answer/` and `envelope/` are §3.3's JSON-text rules, which the Go client holds. The crypto and container vectors are checked by `age` and `ssh-keygen` themselves (`testdata/vectors/README.md`).
- 🛑 **Outside the vectors the script is held to the Go client only where a difference would let through a forgery, a replay, a message its keys did not decrypt, a signature it should not make, or a pass sent where a network can read it.** Such a difference is a defect: it becomes a vector, then a fix in the script. Any other difference (how curl reads a malformed answer, how jq spells a number, a platform's sed) is not one: file nothing and add no workaround, and remove a workaround that guards none of the five.
- **The Go client is the reference** and never changes to match the script.

### Sending

- **What is encrypted is the envelope's line, its signature, then padding** (`protocol/signed.go`, `seal` in `client/send.go`, `dr_seal`; `PROTOCOL.md` §9.2; decided on #29). It is git's layout for a signed tag, with three rules for a reader taken from what went wrong in git's verifiers (`PRECEDENTS.md`, Part 2, § 3): verify line 1 exactly as decrypted, never anything rebuilt; each part has one place, and nothing after the first END line is read; one signature, one identity, the verifier's exit status.
  - 🛑 **A change to how a reader takes the parts apart breaks one of those rules:** `OpenSigned` and `dr_open` are held to each other on every `plain/` vector (`TestVectorsPlain`), code for code where the script can give the code.
  - 🛑 **A format's overhead is a fixed number of bytes, never a share of the message:** so the envelope is never base64 inside a JSON object.
- **Every send is padded, at the seal and never before,** with bytes after the signature (`protocol/pad.go`, `dr_padding`; `PROTOCOL.md` §9.3). The block is counted on the ciphertext, from age's file sizes (`SealedSize`), and each client checks the size of what age wrote and refuses a mismatch. No flag turns padding off or on. Change the arithmetic in both clients together: `TestPaddingIsTheGoClients` holds the script to the Go client, and `TestSealedSizeIsWhatAgeWrites` holds the header sizes to age itself, so an age release that changes them fails there first.
- **A mailbox reads the recipient's mailbox before it posts, and seals to what it then holds** (`readMailbox`, `resolve`, `post`, `trySend` and `seal` in `client/`, `dr_lookup`, `dr_post`, `dr_seal`; `PROTOCOL.md` §11.8, §12.2, §12.5; decided on #55, #91, #112 and #22).
  - **The read comes before anything is sealed or posted, at every post,** a new message or one that waited: one `GET /v1/<address>`, which carries the prekey and what the server holds of the mailbox's revocations. A read of a mailbox carries no pass, of another mailbox or its own (`lookup` in `client/api.go`, `dr_look`; §11.8, §11.5; decided on #214 and #352): the read is public, and a server reads none on it.
  - 🛑 **No answer holds the message in the outbox:** a failed read's code is never read as an answer about the message, never passes through `undeliverable`, and never moves an entry to `outbox/failed/` (`lookupError`). "None held" is kept nowhere: nobody signs it, so it has no lifetime, and the one a cache would need is nobody's to invent.
  - **A seal is made for one post and never kept.** The outbox holds the envelope alone, as written; every post, a retry included, dates it last, once the recipient's mailbox is read, never before it was written and never more than `protocol.TTL` after (its `sent_at` and no other member: the outbox is the mailbox's own, so `seal` writes the line again with `Envelope.Line`, and `dr_seal` with jq, on the envelope the script has just built, each read back as the envelope it was, by `sameEnvelope` and in `dr_seal`; decided on #195, #278, #279 and #357), and seals it to the statement `resolve` passes then, signed by the signer in use. 🛑 **Do not keep a seal to post again:** each check a kept seal needs (a revocation since, a renewal recorded since, a seal cut short: #112, #91, #113) grows with every finding, and all it saves is a lost answer's one send, which the reader's `(from, msg_id)` check already makes harmless. `TestAPostIsDatedAtThePost` holds the outbox to envelopes alone.
  - **A mailbox signs no message by a signer it holds revoked** (`seal`, `dr_seal`; decided on #177), **nor under one whose working key a statement it did not make shows another holds** (`seal`, `NotMade.OwnCertificate`; #428): the entry waits in the outbox, and once `recv` or `prekey renew` has the renewal taken, the next flush seals it under the new certificate.
- **Whatever verifies is kept, from a server or from a file** (`Ask`, `KeepRevocation`). A record handed over is refused whole when a part of it does not verify, and its owner is told (`KeepRevocation`); a server's answer that does not verify counts as nothing shown.
- **A sender holds what it writes to a reader's rules before anything is kept** (`NewJSONEnvelope`, the read-back in `sendWith`, `dr_send`'s `dr_envcheck`; decided on #20): a body or subject its reader would refuse is refused whole, never repaired, so a name given twice is never kept once. An envelope that `seal` would refuse is never written to the outbox, where it would wait for good.
- **A prekey serial is signed once** (`Rekey`, `dr_renew`; decided on #120 and #190): a renewal the server did not take is sent again as it was signed, and a new key goes to a later number only in the cases `Rekey`'s doc comment lists. Signing the same key again with a later `not_after` gives a server that fails renewals and keeps the uploads one key without end.

### Reading what others wrote

- **A mailbox never asks the server who a sender is, and pins one only once its signature verified** (`judge`, `pin`, `dr_meet`): the envelope carries the identity document, whose hash is the sender. The one thing it asks about a sender is whether a revocation of it exists, by one read of its mailbox, once in a drain and only after that sender's signature verified. On a send, a peer is pinned only once something its identity signed has verified.
- **The Go client decrypts a file only with exactly one native recipient stanza** (`oneNative`; `PROTOCOL.md` §12.3 check 1; decided on #49): age tries every prekey on every stanza, up to 1,024, and only a server can serve such a file. The stanzas are read and counted once, by `protocol.ReadStanzas`, which dromas-server's check of a send shares, and a file with none is a case of its own (§11.10 step 7). 🛑 **They are counted before age is given any prekey** (`decrypt`): a check inside an identity runs after age has tried those it sorts first, and one any prekey skips lets its key agreements through (`TestNoKeyAgreementBeforeTheStanzasAreCounted`, `TestTwoNativeStanzasOneToARetiredPrekeyAreRefused`, `TestAFileWithoutOneNativeStanzaIsRefusedUndecrypted`).
- **A fetch is read to the size its list gives, and no further** (`ciphertext` in `client/api.go`, `dr_one`; `PROTOCOL.md` §12.3): the fetch answers the ciphertext alone, and the list says how long it is and when it came: who sent it is its signature's. A body of another size is an answer that breaks its form, and stops the drain with nothing judged or acked.
- **A fetch that is cut goes on from what it kept, by range** (`client/partial.go`, `PROTOCOL.md` §12.3; decided on #381): the whole, the bytes kept and the range, is held to the list's size and judged as a body read whole is, its id to its SHA-256 (§12.3 check 8), so bytes a server splices in are refused as any wrong ciphertext is, and a `206` that is not the range asked breaks its form. 🛑 **The partial file is written in place, so it is trusted only as far as the mailbox's state records it synced:** the record is written after the file and its directory are synced, and deleted before the file is cut short or holds another message's bytes. A fetch that took the file's own length could judge bytes a crash left unsynced, refuse a message an honest server holds, and ack it.
- **The replay set keeps each line `protocol.SeenFor` from its `sent_at`, and is pruned by the mailbox's clock only once the server has taken that drain's pass** (`pruneSeen`, `dr_forget`; `PROTOCOL.md` §12.3 check 8; decided on #196). 🛑 **A prune that drops a line raises the floor to its cutoff FIRST, or in the same transaction (the Go client's state), and a `sent_at` below the floor, or less than `protocol.TTL` above it, is `stale`** (`seenFloor`, `dr_floor`; decided on #279): pruned before the pass, or with no floor, a clock that steps back makes a delivered message fresh again, and a hostile server replays it (`TestAReplayIsRefusedAfterTheClockStepsBack`); a retry is dated up to a TTL after its first copy, so a floor that held its own `sent_at` would let a kept retry through (`TestARetryAboveTheFloorIsDeliveredAgain`).
- **Keys are deleted, and the replay set pruned, by the mailbox's clock only once a server has taken a pass dated by it, and by that pass's date, never by a reading of the clock** (`taken`, a `client/internal/taken` reading whose one constructor reads a pass, `ownerTaken`, `publish`, `Result.listedAt`, `prune`, `dropRetired`, `pruneSeen`; `dr_taken`, `DR_LISTED`, `dr_prune`, `dr_forget`; decided on #200, #259 and #266): a drain's list answered, or a renewal taken. A clock far ahead is stopped at its pass, one that jumps or steps back while the call is in flight deletes nothing by where it went, and the keys that messages wait for stay (`client/taken_test.go`). 🛑 A new path that deletes by the clock takes a `taken`, which only a pass the server took gives (`taken.By`; its zero value, no reading, deletes nothing): never `b.now()`, nor a reading taken just before or after the call.
- **A drain is bounded** (`maxDrain*`, and in time by `DefaultDrainTime`, `recv --drain-time`, which a fetch cut there goes on from at the next recv), and one the server paces (`429 fetch_paced` with `Retry-After` on a fetch) stops as at those limits, with `Result.Paced` and no error: the rest waits on the server. `recv` says to run again after `Result.Again`, the later of the pace and the poll interval, since the next run begins with a poll, and `recv --wait` waits the same.
- **A `304` answers only for the tag its poll sent** (`sameTag` in `drain`; `PROTOCOL.md` §12.3; decided on #149): one about another tag is no answer: no retired prekey is dropped on it (`dropRetired`), the replay set and the prekeys past their deletion time are pruned as on any list the server answered, and the kept tag goes (`TestA304AboutAnotherTagIsNoAnswer`). The fake reads `If-None-Match` through `protocol.IfNoneMatch`, as dromas-server does: `*` only as the whole value, each tag through its closing quote. 🛑 Never split it at commas: one planted tag would make every poll `304`.
- **A signature has one form, the bytes the Go client and `ssh-keygen -Y sign` write** (`protocol.Dearmor`, `oneForm`, `dr_blob`, `dr_sshsig`; `PROTOCOL.md` §3.2; decided on #580): a verifier parses it, writes it back in that form, and refuses any difference, as `ParseIdentity` does a document; ECDSA's (r, s) and (r, n − s) are each a signature in that form, and both are taken (`lowS` where one is compared to another); then at most the bound its identity's key type sets (`protocol.SignatureBound`), and an Ed25519 S below L. `sshsig/` stays x/crypto's API, and a Go verifier gets the form through `Dearmor`. 🛑 **`ssh-keygen -Y verify` is a test of a signature, never its definition:** it takes forms the spec refuses (Appendix A), so the script holds the form itself, never through `ssh-keygen` alone; `TestVectorSignatureForms` in `protocol` and `TestVectorsSignatureForm` in `sh/` hold both clients to one verdict on each `sig/` vector, and `ssh-keygen` to taking each `ok-`.
- **Every JSON text is read by one set of rules, by every reader** (`protocol.Unmarshal`, `protocol.UnmarshalRequest`; `PROTOCOL.md` §3.3; decided on #66 and dromas-dev/dromas-server#17). A server refuses a member it does not know in what it is sent, and every other reader ignores one (a client in an answer, a mailbox in an envelope), and the rules hold in it.
  - **The parsing is Go's `encoding/json/v2`, so the module needs Go ≥ 1.27.** A check beside it is one it does not make (depth, noncharacters, the integers). 🛑 **Never `encoding/json`'s `Unmarshal` on a text a server, a sender or a file brought:** it matches names in any case and keeps the last of a name given twice. Writing with it is fine.
  - **The script reads with jq,** and holds a text to §3.3 only where the five need it (§ The shell client): an envelope is one object with no member named twice (`dr_envform`), and each value it uses has its form where it reads it (`dr_shape`; `dr_bytes`, whose one-encoding check makes a byte field one text on GNU's base64 and uutils' alike; and the checks beside each use). jq ≥ 1.7.1 is needed: 1.7.0 can abort on a number a sender writes (CVE-2023-50246).
  - 🛑 **A shell variable drops trailing line feeds and every NUL,** so a value a check depends on is tested in jq or compared as bytes, never through `$(…)`.
  - 🛑 **The script runs in the C locale** (`export LC_ALL=C` at its top), so its patterns and every tool it runs read bytes, as the Go client does: under en_US.UTF-8 `[0-9]` takes a digit that is not ASCII, and under tr_TR.UTF-8 `[A-Z]` misses `I`. `TestTheScriptReadsBytesInEveryLocale` runs the vector tests under both.
  - **A serial is at most 2^53 − 1 everywhere** (`protocol.MaxSerial`), since an answer names one as a JSON number. A JSON member that is a number is exactly `int64` or `uint64`, the two `integers` reads: never `int`, `uint` or `uintptr`, whose width is the build's, nor another width, a float or a type declared on one (`TestWireIntegersHaveAFixedWidth`, which type-checks the package); `int` is for what stays in the process.
- **An identity is a key of a type `PROTOCOL.md` §4.1 defines** (`identityTypes` in `protocol/identity.go`, `dr_idcheck`; decided on #21): `ssh-ed25519`, which every client makes, or `ecdsa-sha2-nistp256`; every client verifies both.
  - **A type is added in both clients together:** its key checks, its signature bound, and a vector for each document a client must refuse. Its form is the one every type shares, the key in its one encoding, the wire key as written back once parsed (`ParseIdentity` compares the two; `dr_idcheck`, `ssh-keygen -l`'s fingerprint with the wire's hash): never a pattern of its own. Where the Go library and `ssh-keygen` differ on a key, the stricter rule goes into the spec and is made explicit in the other client, so one document gets one verdict (`TestVectorBadIdentities`, `TestVectorsIdentity`).
  - **A well-formed document of a type a client lacks is `unsupported_key_type`, never `bad_identity`,** and only once it is known to be the sender's: a malformed document points at tampering, one of another type does not.
  - **So is a prekey of a type a client lacks** (`protocol.ErrPrekeyType`, `RefusedPrekeyType`, `dr_bech32`, `dr_prekeycheck`; `PROTOCOL.md` §6; `prekey/unsupported-type*`): a statement whose key is a well-formed age recipient, a Bech32 string whose human-readable part begins `age` and is not `age1pq`, X25519's `age` among them, is refused at a send as `unsupported_prekey_type`, never as one that does not verify, and the key's type is the last thing a statement is held to. 🛑 The script reads the type before it runs `age -r`: age ≥ 1.3 encrypts to more types than the protocol defines, an SSH key among them.
  - **Every client verifies every type §4.1 defines; with each prekey it declares only the optional types it verifies** (`sender_key_types`, §7; `protocol.OptionalTypes`, the declaration; `protocol.Declaration`, what a server keeps of one; `protocol.AcceptsSender`, both clients' and dromas-server's one test of a sender): never a §4.1 type. The script verifies no optional type and declares nothing, and refuses an `ssh-keygen` that reads no P-256 key (`dr_p256`). A type other than Ed25519 is never what a client makes by default, and `init --identity-type` of an optional one warns.
  - 🛑 **Nothing may rest on a certificate having one set of bytes:** one an ECDSA identity signed has a second, with (r, n − s), which anyone can write and both verifiers take (`TestAP256IdentityCertifies`).
  - 🛑 **The script compares a document with itself rebuilt, byte for byte** (`dr_idcheck`): a shell variable drops a NUL, so a test of the variable alone passes a file that holds one (`identity/nul-*.doc`).
  - 🛑 **An identity key's checks live in `protocol.ParseIdentity`, not in `sshsig`** (Ed25519: no point, small order, non-canonical; P-256 has none beyond the point x/crypto reads, as OpenSSH from 10.3p1, decided on #354): x/crypto's would not make them, and every identity a verifier uses has passed `ParseIdentity` first.

### Signers and the working key

- **A mailbox signs with its identity, or with a working key under a certificate its identity made, and every verifier takes both** (`protocol.Signer`, `protocol.VerifySigned`, `protocol.Admits`, `client/internal/sign`; `PROTOCOL.md` §5; decided on #30, #579 and #594). A verifier takes the identity's signature always, and a certificate above the revocation of certificates it holds for the address; a revocation of certificates never covers the identity, which only the revocation of the address ends.
  - **`sign` has two signers:** `Identity` (statements, passes, messages, certificates and revocations, at any time) and `Work` (statements, passes and messages under its certificate). Every signature asks `finished` first; the address's own revocation can always be signed. 🛑 A new way to sign goes in `sign`, never around it.
  - 🛑 **A rank is compared as a number,** 0 for the identity and its serial for a certificate, for the order `(c, p)` alone; a revocation of certificates is held against a certificate's serial, never against rank 0. The code branches on the signer's form there, and to read a certificate's own fields; never on a serial of 0.
  - **A revocation of certificates is applied by what each party holds, where it already reads:** a reader at check 7, never at check 5 (`judge`, `dr_judge`); a sender at its read before every post, which keeps the `(c, p)` floor too (`resolve`, `dr_resolve`); the server by what it keeps.
- **`init` makes a mailbox whose identity signs; `init --offline` one that registers under a certificate at once.** A mailbox moves to certificates by renewing under one, `dromas cert switch <address>`, which takes the address in full (`PROTOCOL.md` §12.4): its statements are under certificates from then on (§5.3), what it signed with its identity stays good, and nothing is posted again. `cert revoke-earlier` is refused for a mailbox whose statements its identity signs. A restore renews under a certificate where its server serves one, and by its identity otherwise unless `--offline`.
- **A mailbox under a certificate makes a new working key and certificate with each new prekey,** and keeps it as `work/<serial>` in the names `ssh-keygen` uses (`client/work.go`, `protocol/certificate.go`). The working key's type is the one its identity's type gives (`protocol.WorkingKeyType`, §4.1's column), held by `checkWorkingKey` and made by `newKey`: a type is added with its working key's type in the same entry (`TestEveryIdentityTypeNamesADefinedWorkingKeyType`). A certificate asks for the server's maximum (`max_certificate_lifetime`, §11.18), dated `protocol.MaxSkew` back; no message is signed under one with `protocol.TTL` or less left, and the client refuses to sign under a certificate at a server whose maximum leaves no room for that, and says so. A verifier sets no ceiling: both dates at or before `protocol.LastDate`. `CheckCertificate` checks one certificate against an identity and a clock; holding its serial to an order is the caller's (`Resolve` does, for a peer's prekey statements).
  - 🛑 **`ssh-keygen -Y verify` takes a certificate with a critical option, extensions out of the one encoding the Go client's library reads, another key id, serial 0 or a validity of `forever`,** so the script reads a certificate's fields from its bytes: `TestVectorsCertificate` holds that, with a `cert/bad-*` vector for each rule. A certificate carries no extension, an empty `reserved` and a 32-byte nonce, the one form `ssh-keygen -s … -O clear` and the Go client write (`PROTOCOL.md` §5.2).
- **A mailbox proves itself with a pass it signs, and there is no token** (`protocol/pass.go`, `pass` in `client/work.go`, `dr_pass`; `PROTOCOL.md` §8; decided on #36). A client writes it in one form, and `ParsePass` reads it as RFC 9110 §11 lets a recipient (decided on dromas-dev/dromas-server#18): `FuzzParsePass` holds that every form it takes reads as the values of that one form, and `testdata/vectors/pass/` has each form taken and refused. `Pass.Authorization` writes the one form back, a P-256 signature's s as the lower of s and n − s (`lowS`), so a server that remembers passes by it checks each once however its header is written and whichever s it carries (`TestAPassWrittenAnotherWayIsOnePass`). The pass is kept in the mailbox and used until 30 seconds before it runs out; if a server refuses it, a client signs another and tries once more (`passRefused`, every 401; `TestEveryRefusalOfThePassIsTriedUnderANewOne` reads its codes from the code). A pass is signed by the current statement's signer; a registration and a prekey upload carry a pass by the signer of the statement they bring (`publish`), kept only once the server took it. 🛑 **Nothing a server sends is decrypted with a key that reads messages.**
- **A mailbox's statements are ordered by `(c, p)`:** the signer's rank, then the prekey's own serial (`protocol.Order`, `PrekeyOrder`, `Resolve`, `rekey`, `readOwn`, `noteServed`, `signedPrekey`, `dr_resolve`, `dr_renew`; decided on #48 and #579). A later signer passes any serial under an earlier one, so every certificate passes the identity, and a renewal's number is above the served statement's under the same `c`. 🛑 **Never compare prekey serials across signers** (#48): one use of a taken working key, at the highest serial there is, would end the address.
- **A certificate's serial is its maker's clock in seconds, or one above the highest serial the mailbox knows of when the clock gives nothing higher** (`protocol.SerialAt`, `Init`, `rekey`; decided on #63; the script makes no certificate, and numbers its statements by its clock in `dr_init` and `dr_renew`). The prekey and working key made with it share the number. A mailbox restored from its identity alone is, by the clock, above every certificate made before, so the revocation of everything below it covers them all.
  - 🛑 **A verifier never reads a serial as a time: it compares two.** Add no check of a serial against a clock, anywhere.
  - 🛑 **"One above" stays; do not make it a refusal** (weighed on #73): it covers two renewals in one second, and a lost machine's fast clock, where a refusal would hold back the owner's renewal and revocation (`TestALostMachinesFastClockDoesNotDelayTheRemedy`).
  - 🛑 **A number an attempt took is kept until its statement is published or spent** (`highestBegun`, the renewal under way in the mailbox's state, recorded before anything is made: `begin`): a new number for every retry would sign a new key each time and leave the waiting one unsent. A statement is kept with when it was signed in one value, and its working key is always made new for it (`makeWork`; #192, #197). `Init` is a renewal like any other, read from the mailbox's server first (`known`; #87), but for an identity it made itself, which no server holds anything of: that one registers with no read, which a server would count as a miss of its address.
  - **A renewal the server took is recorded before anything else is done** (`publish`, `recordTaken`), and a fault of the mailbox after that comes back beside the new prekey, never as a renewal not taken (#110): whether one was taken is the mailbox's state's to say, never the upload's answer, but where a fault of the mailbox kept it from recording one the server answered (`tookRenewal`; `TestAnUploadAnswered404WhoseReadAgainServesItIsTaken`, `TestAFaultRecordingARenewalTheServerTookLeavesItTaken`). One whose answer the mailbox never had, its process ended in between, is recorded at its next read of itself that serves it under the certificate made with it (`noteServed`), which a pass refused as `certificate_not_current` sends it to first (`ownerTaken`). One that failed is kept with why, and tried again `renewRetry` after it by whichever process runs then, unless it is dated after the clock (`renewIfDue`; #10, #201).
  - **A served statement the mailbox did not make is said** in `status`, recv's exit status 3 and `prekey renew`'s output, by its kind, signed by the identity, or under a certificate the mailbox made or not (`certifiedHere`, which compares the key certified, never the certificate's bytes), each recommending that the address be revoked (`NotMade`; #74, #428, #579), and once its server has taken a statement of the mailbox's own above it, naming that one (`RenewedAbove`, written by `recordTaken`; #599): a renewal takes the address back, never the identity. Where the mailbox's statements are its identity's, the owner's `prekey renew` goes on, and the outbox is not held: no certificate of the mailbox's own is in doubt. 🛑 **A renewal the mailbox makes on its own renews nothing above one, once the mailbox has published a statement of its own** (`renew` with `asked` unset: Receive's, through `renewNow`; `readOwn`): only its owner judges whose it is, and `prekey renew`, `init` and the remedy, which an owner runs, renew above it (`TestRecvRenewsNothingAboveAStatementTheMailboxDidNotMake`). A mailbox that has published none is a restore, from its identity alone or a lost state file, and its recv renews as before (#366).
  - **A mailbox judges its own record at its server by every rule but its certificate's dates** (`VerifyPrekeyRecord`, `CheckCertificateRecord`; `PROTOCOL.md` §12.4): one its server took under a rule since changed, made for longer, begun earlier than a client dates one, or ended, is renewed past; one that does not verify, or a rollback, stops a renewal and names `dromas cert revoke-earlier`, which goes on past it (`TestARenewalGoesPastItsOwnRecordWhateverItsDates`). 🛑 Judged at its certificate's start, a record made for longer than a client dates one is one its mailbox could never renew past (#428).
  - 🛑 **A test reads a mailbox's number and never assumes one** (`numberOf`, and `num` in `sh/world_test.go`).
- **A send names its prekey statement by `statement`, the SHA-256 of the statement's bytes as served, in its query, and its body is the ciphertext itself** (`protocol.StatementHash`, `protocol.SendQuery`, `postSealed`, `dr_seal`, `dr_post`; `PROTOCOL.md` §11.10): never a hash of its signature, which another encoding of an ECDSA signature changes, and the age file's bytes as they are, never base64 inside JSON.

### Revocation

- **An address is revoked by its identity's own signature, and a client takes "revoked" on nothing less** (`protocol/revocation.go`, `client/revocation.go`, `dr_revcheck`, `dr_gone`, `dr_lookup`; `PROTOCOL.md` §10.1; decided on #14).
  - **A server's `revoked` or `sender_revoked` is checked, never believed:** `proved`, which every answer passes (`call`; `provedLocked` for `Hold`'s, made outside the mailbox's lock), takes the record a `410` carries as the read's is taken (`take`), and reads the mailbox the call names for one only where it carries none that verifies and the call was not that read, or itself after a `sender_revoked` (decided on #353); only a record that verifies makes a `RevokedError`, and without one the call has failed and no state changes. 🛑 No code `proved` checks (`provedCodes`) may go back into `undeliverable` (`TestNoAnswerProvedIsUndeliverable`, `TestAServersWordAtAPostEndsNoMessage`).
  - **A revocation that verified is kept and never removed** (`keepRevocation`, in the mailbox's state, the mailbox's own beside its other records), read and checked again at each use. `Resolve` refuses such a peer before any request, and `judge` refuses its messages, whenever they were signed.
  - **A mailbox that holds its own revocation signs nothing more,** whatever any server answers (decided on #152). The identity and the working keys sign only through `client/internal/sign`, whose every signature asks `finished` first (`TestOnlySignSigns` holds the module to it); `locked`, the one entry of every command that writes the mailbox, refuses such a mailbox before anything is asked, and `lockedFinished` runs what §12.5 lets it still do: asking about and keeping a revocation, a flush, which moves what waits to `outbox/failed/` (each entry by the mailbox's own `ended`, `TestAFlushThatLearnsItsOwnRevocationMovesEveryLaterEntry`), and a change to the mailbox's own files (`TestAMailboxThatKeepsItsOwnRevocationSignsNothingMore` runs every command that takes the lock, and `TestEveryLockingCommandIsTriedFinished` holds its list to the code); keeping the mailbox's own revocation drops the pass it kept, and `pass`, the one place a call gets one, gives none. A command that learns it part way says that alone and asks nothing more, at three places: the event is the keep (`keepRevocation`, of the mailbox's own address by a command that began with none, which drops the pass, a failed renewal and a read of its server's ACL owed too); the proof once, where every answer passes (`proved` in `call`, by the address the answer names: a read is proved by what it carries alone, so a proof's reads are not proved again, `TestARevokedReadWhoseRecordDoesNotVerifyIsNotReadAgain`), and after the event `call` asks nothing more (`TestACommandThatKeptItsOwnRevocationAsksNothingMore`); the outcome at `locked`'s exit, the revocation alone beside what the command did (`outcome`, which `Init` takes too and `lockedFinished`'s other commands do not: finishing the mailbox is what some are for). A read of itself that shows the mailbox its revocation returns it as its error (`known`), so a renewal stops before it begins anything (`TestARenewalThatMeetsItsOwnRevocationSignsNothing`). `TestEveryCommandShownItsOwnRevocationAtEachCall` holds the three: every command `locked` runs, in the states that reach each of its paths, its server made hostile at each call an honest run makes, kept, said and nothing asked or made after; a new command or path gets its case there. The script: `dr_finished`, in `dr_post`, `dr_drain`, `dr_renew`, `dr_pass` and `dr_prekey`. What carries no pass still goes: `status`, `revocation ask`, `revocation keep`, publishing again (`Mailbox.Revocation` gives the record the mailbox holds), `cert publish-revoked`. 🛑 A new way to sign goes in `sign`, and a new command takes the lock through `locked`.
  - 🛑 **A working key's signature is not a revocation:** `VerifyRevocation` verifies against the identity's bare key, and the script's signers line for a revocation is always the plain one, with no `cert-authority`, whatever is revoked (`revoke/bad-by-a-working-key.sig`). For anything else the line is one, chosen by the signing key's form.
  - **A negative answer and no answer are different things** (`lookupRevocation`, `dr_lookup`): a mailbox served with no revocation, no such mailbox, or "revoked" with nothing that verifies lets a drain go on, and anything else stops it with the messages still on the server.
  - 🛑 **The statement is fixed text and never gains a field.** What is added later is a second statement under a new tag: a slot nobody fills fails when it is used, and a rule to refuse what a reader does not understand would turn a revoked address back into a live one.
  - **A record names its own type, `"type":"revocation_record"`** (`Revocations.MarshalJSON`, `checkType`, called by `Unmarshal` and `UnmarshalRequest`, and on the `record` a problem carries). Every writer writes it, in no set order (decided on #355), servers in their answers too, and the client first, as it prints every line; a reader takes a record without it and refuses one that names another type (`ErrMemberValue`, `400 bad_request` with `member`). So the line `revocation make` prints is the record, the body every server takes: never print a record with anything beside its own members.
  - **`revocation publish` takes the address in full as its confirmation,** and neither client writes a record unasked: kept beside the identity, it is lost and stolen with it.
- **Certificates are revoked through a serial their identity signs: the highest one verified stands, nothing lowers it, and it covers certificates alone** (`protocol/revokedcerts.go`, `client/revocation.go`, `dr_certscheck`, `dr_certrevoked`, `dr_keepcerts`; `PROTOCOL.md` §10.2; decided on #51, #79, #579 and #594). Both kinds of revocation verify under the identity's bare key and are kept, whatever is revoked: neither is ranked.
  - **It is verified as a revocation of the address is, under the identity's bare key, then parsed exactly** (`revoked/bad-by-a-working-key`). The script compares the file with itself rebuilt, and compares serials in bash, whose integers are exact.
  - 🛑 **There is no version and no list: do not add a way to revoke fewer.** One that does not verify or runs no higher changes nothing, whenever it arrives, and a certificate once revoked is never taken again. What is kept is checked again at each use, and one that no longer verifies is an error, never "nothing revoked".
  - 🛑 **It is kept as ONE value, the statement with its signature** (`keepRevokedCerts`): a statement and its signature written apart can be left one new and one old by a crash, a pair that never verifies again.
  - **A revoked certificate loses everything signed under it, whenever it was signed:** `judge` and `dr_judge` refuse its messages as `certificate_revoked`, and `Resolve` and `dr_resolve` refuse a prekey statement under it. The address and the identity's own signature go on.
  - **A mailbox never makes a certificate its identity has revoked** (`rekey`): the next is numbered above the highest serial it holds revoked, and every renewal first takes what the read of its own mailbox carries (`readOwn`, and `dr_renew`'s `dr_take` in the script; decided on #82). One through 2^53 − 1 leaves none to make, and the mailbox says so.
  - **`cert revoke-earlier` runs `RenewAndRevoke`,** for a mailbox under a certificate alone (`client/revocation.go`; `PROTOCOL.md` §12.6; decided on #162, #163, #164, #111 and #130), whose doc comment has its steps. 🛑 **The revocation goes first, whatever the renewal meets:** once a server holds it, whoever holds the taken working key can spend none of the mailbox's calls there. A mailbox whose own revocation covers the certificate it uses renews at its next drain (`renewIfDue`, `ownRevokes`). The script applies one and makes none, and has no remedy.
- **A mailbox asks about revocations, and publishes its own, at its own server alone** (`readMailbox`, `publishRecord`; `PROTOCOL.md` §12.5; decided on #311). Every server keeps and serves a revocation of any address, with a mailbox there or none, and a mailbox reads `GET …/revocations` where its server holds no mailbox for it. 🛑 **A mailbox reads its own state at its server through `known` alone,** `GET /v1/<own>` and those revocations, keeping what verifies (decided on #258): a renewal, the remedy, a renewal's upload answered `no_such_mailbox`, which goes as the registration only where that read shows no mailbox (`sendRenewal`, every renewal's; `PROTOCOL.md` §12.4; #386; `TestARenewalWhoseUploadMeetsAMailboxForgottenSinceItsReadRegistersIt`, `TestARenewalWhoseUploadIs404RegistersOnlyOnAReadThatShowsNoMailbox`, `TestARenewalWhoseReadAgainEndsSendsNoRegistration`), a question about its own address and a `410` that carries no record that verifies all decide from it, and none reads part of it itself.
  - **A `410` to a published record is taken only once a record the server shows verifies** (`proved`, then `served`): the one the `410` carries, or the one its read of the mailbox then carries, kept (#153), and by a publish with no mailbox only checked. So is a `409` to a revocation of its own certificates, whose higher record the mailbox reads and keeps (`Mailbox.Publish`, and once in the remedy: `revokeBelow`).
  - **A server's `401 certificate_revoked` to the mailbox's pass is checked as its `revoked` is** (`proved`): the mailbox reads itself, before any pass is tried again, and only a revocation that verifies and covers its certificate makes it a refusal, after which a send waits in the outbox and a drain renews and drains again, once, as it does when its server holds no mailbox for it (`mendable`).
  - 🛑 What ends an address goes out only with that address written in full: `cert publish-revoked` takes a revocation of certificates and no revocation of the address.

### Who may write to a mailbox

The client holds; the server's ACL refuses (`protocol/acl.go`, `client/senders.go`; `PROTOCOL.md` §12.3, §11.14; decided on #4 and #23).
- **`held/` is not `refused/`:** refused holds messages that failed a check, held holds messages that passed from an unknown sender, one the mailbox has not allowed. Keep the two words and directories apart.
- **A policy, `allowed` or `blocked` file that cannot be read stops a drain and a send** (`readSenders`), and is never read as the default.
- 🛑 **An ACL always says whom it lets in:** `Document` writes both lists, an empty one as `[]`, and `CheckACL` refuses one with no `allow`. Never let a writer drop an empty `allow`: an ACL without one would read as everyone.
- **The ACL goes before the post when it changed, and a post waits for it only when the ACL the server last took does not admit the reply** (`SendWith`, `Flush`, `replyWaits`; decided on #180): a reply the server refuses for it is final, and one it takes is posted, with `acl_not_sent` said, as `recv` says it. `sender_not_allowed` is in `undeliverable` and in the script's list.
- **At each renewal `recv` makes, about daily, the mailbox reads the ACL its server holds and puts its own where the lists differ** (`checkACL`, `aclAt`; decided on #360): one another writer put there, another machine of the mailbox or someone holding its pass, lasts until the mailbox's next renewal at most, and `recv` says so (`acl_replaced`, exit 3). 🛑 It compares the documents, never a tag, whose making is the server's own; and a drain or a send reads no ACL (`TestARenewalReplacesAnACLAnotherWriterPut`, the state table).
  - 🛑 **A fault never skips the record** (#377): the read is owed in the mailbox's state from before the renewal (`oweACLRead`), and when it is made and reported is `receive`'s and `Result.ACLReplaced`'s; what it showed is kept before the mailbox's own is sent, marked as another writer's (`keepHeld`), so a PUT not taken leaves the mailbox's own pending; a registration drops the mark with the ACL (`TestARenewalWhosePUTIsNotTakenLeavesTheMailboxsACLPending`, `TestARecvKilledAtEachStepOfItsRenewalReadsItsServersACL`, `TestAnACLReadNotMadeIsOwedToTheNextRecv`, `TestARegistrationDropsTheMarkOfAnotherWritersACL`). Where its ACL is not taken, the mailbox says what changed (`aclWhy`; `TestWhatChangedInAnACLNotTakenIsSaid`).
- **A mailbox restored from its identity alone, with none of its `allowed`, `blocked` and `policy` files, adopts the ACL its server holds** (`beginAdoption`, `adoptPending`; decided on #366): its empty files would make the open ACL, and the heal would replace every block the server held. The renewal marks it before anything is signed, and once one is taken the mailbox reads `GET …/acl` and adds its entries to its lists, before any ACL is compared or sent; a registration adopts none, since its server holds no ACL of a mailbox it forgot, and a mailbox restored with any of the three keeps its files as its ACL (`TestARestoredMailboxAdoptsItsServersACL`, `TestARestoreKilledAtEachStepAdoptsItsServersACL`). What no file can say (a deny of `*`, or addresses beside an allow of `*`: `unsaid`) goes with the mailbox's first ACL, and recv reports that as `acl_replaced`, as the heal's, whichever sync sent it (`replacedNote`; `TestARestoredMailboxReportsWhatItDidNotAdopt`). An answer over `protocol.MaxACLEntries` is one that breaks its form: nothing is adopted, and the read is made again (`heldACL`; `TestARestoreAdoptsABoundedACL`; #440). 🛑 A hostile server can lie there once: an `allow` entry it adds lands that verified sender's messages in `inbox/` and not `held/`, and a `deny` entry has the mailbox drop messages the server could drop anyway, each kept in the mailbox's files until its owner edits them; it forges no sender.
- **The owner's lists are read by one reader** (`addresses`): blank lines and lines starting with `#` are skipped, as in `policy` (#181), and blocking wins: `peer allow` of a sender `blocked` names does nothing (#179).
- **Tests:** `env.mailbox` lands every sender's messages, since most tests are of what comes before landing; a test of where a message lands makes its mailboxes with `heldMailbox`. `sh/sh_test.go` (`landAll`), the server's tests and its `test/interop.sh` (`gocli`) do the same.

### What a mailbox prints

- **Every command prints JSON lines, one object a line, its `type` first** (`line`, `typed` and `report` in `cmd/dromas/output.go`; `dr_out`, `dr_err`, `dr_wrong`; decided on #17 and #18). What a command did and met goes to stdout, so a reader of stdout alone misses nothing; stderr has only the `error`, `usage_error` and `waiting` lines. A `detail` is the client's own words. Help is the one thing printed as text, and nothing switches on whether stdout is a terminal.
  - 🛑 **A line is built by `line` or `typed`, never by formatting text into JSON,** and a message line's `envelope` is the `inbox/` line's own bytes (`raw`): encoding it again would write raw the line breaks it escapes. A new line type goes in the README's table in the same commit, and in both clients where the script has the command.
  - 🛑 **The envelope's members are only ever inside `envelope`,** in a line and in a file the client keeps (`message`, `messageHeaders`, `recordSent`, `dr_recv`, `dr_line`; decided on #356): the envelope may gain members inside v1 (`PROTOCOL.md` §14), and one beside the client's own (`type`, `id`, `receipt`) could take a name the line already has (`PRECEDENTS.md`, Part 2, § 3e). `TestNoLineCarriesAnEnvelopeMemberBesideTheEnvelope` holds every line to it, read from `cmd/dromas`'s source: each `line` and `object` call's names, and each typed line's marshalled type.
  - **A line that is also a protocol document is that document, exactly** (§10.3's record): its `type` is part of the protocol's format, never members added around it.
  - 🛑 **In the script, a line printed inside a function whose stdout is captured is lost** (`why=$(dr_judge …)`): such a function writes to `$DR/said`, which its caller prints.
- **Exit status 3 is "done, and the mailbox needs a look"** (`needsALook`): `recv` after a failed renewal, `status` with a non-empty `attention`. A refused message never changes `recv`'s exit status, because any sender can cause a refusal.
- **Nothing someone else wrote is printed as this client's words.** A refusal is a code from the closed set in `client/errors.go` and `protocol/envelope.go`, with fixed words: never a value, key or field from an envelope, a served identity or a served statement.
  - 🛑 **A server's words are never printed at all** (decided on #43; `PROTOCOL.md` §11.3): its `detail`, `hint` and `title` are for a person with curl. An API error is its status, a code the client knows under that code's own status and beside its own `type` (`protocol.Problem.CodeAt`, `dr_code`), and the client's own sentence for it (`APIError.words`, `dr_api`), with the members it carries once each is checked to its type, a string member only once it is a value the client knows. A new code gets its sentence in the same commit; `TestAnAPIErrorPrintsNoneOfTheServersWords` puts injected text in every free member of every code; `type` is no free member. 🛑 **Nor is net/http's error printed, which quotes the server** (a status line, a header or trailer line, a `Location`): a call with no answer it could read is named by its method and path, never its query (a list's cursor is the server's), and a kind from a fixed set, read from the whole chain of its error (`transportError`, `noAnswer`; `TestATransportErrorPrintsNoneOfTheServersWords`, `TestAListsCursorIsNeverPrinted`). net/http's own logger, which quotes what a server sends after its answer, writes nowhere: `main` points it at `io.Discard` (`TestTheBinarysStderrHoldsOnlyItsLines`).
  - A receipt is checked against the ciphertext posted before it is printed or recorded, and an account name against its form (#5). 🛑 A new error path that formats outside text with `%s`, `%q` or `%v` breaks this rule: `TestARefusalNeverQuotesTheMessage` and `TestScriptRefusesInItsOwnWords` hold the envelope's.
- **A line a mailbox prints or keeps escapes what nobody sees** (`escapeUnseen`, `dr_line`; decided on #19): each line break but LF, and every character of Unicode's `Default_Ignorable_Code_Point`, as JSON escapes them, so nothing hides an instruction from whoever reads it. The list is Unicode 18.0's, kept in each client: a new Unicode version changes the Go client's, the reference, and the script's beside it. `inbox list`, `inbox show` and `peer allow` print a kept line only when it is, byte for byte, the line recv writes of the record it reads back as (`keptLine`, `keptLineOf`, the one function recv writes with): whoever last wrote the file is not known.
- **`refused/` keeps a refused message whole, as served, with none of the server's strings in the clear but those of their form** (`keepRefused`; decided on #7): an id is 64 lowercase hex and an address one `ParseAddress` reads, a time one `ParseTime` reads, any other string `<name>_b64`. The script's (`dr_kept`) keeps the ciphertext and the id it hashed, none of the server's strings. It is read through `dromas refused list`, which holds each value to its form again, and `status` names that command, never the files.
  - **Beside it, in the mailbox's state, which only it writes, the Go client keeps why it refused it and what its checks established** (`protocol.Examine`'s `Findings`, `refusedRecord`; decided on #44 and #280): a file in `refused/` lists nothing of either (`TestRefusedKeepsNoServerTextInTheClear`), and a later delivery of the message leaves nothing of its refusal (#211). It keeps the clock it judged by, and who signed it only when the signature verifies at its certificate's own start and the mailbox holds no revocation of that address or that certificate (`signed_by`; #265), otherwise the identity it claims (`claims_identity`) alone, and with `signed_by` that certificate's serial and dates and the envelope's `sent_at` and `msg_id`. 🛑 **Never the identity a failed signature carries as its sender, and never anything the sender wrote as text:** a forgery copies an identity to frame it. The script keeps none of it (README § Stock tools).
  - **A refusal for a time is a verdict like any other,** kept in `refused/` and acked (`PROTOCOL.md` §12.3; decided on #44). 🛑 Do not hold such a message on the server to wait for a clock: a client whose clocks are right makes none, and the mailbox's owner judges the rest.
- **A secret is never an argument** (decided on #15): `account adopt` reads the key on stdin, holds it to an adopt key's form before anything is sent, and never prints what it read.

### The command line

`dromas <command>`, or `dromas <group> <command>` where one thing has more than one thing done to it (`cmd/dromas`, on cobra, as gh and docker are; decided on #37). A renamed command keeps no old name: before the freeze there is nobody to keep it for. `sh/dromas.sh` takes the same words for the commands it has.
- **Help in every form a git-like tool gives it** (clig.dev): `dromas help [<command>]`, `--help` after any command, and `<group> help`, to stdout with exit 0. 🛑 **`--help` that pflag reads as the help flag prints the command's help and runs nothing,** wherever it is after the command: `revocation publish` with the address in full and `--help` publishes nothing (`TestHelpRunsNothing`, and `TestTheCommandLine` in `sh/`). It is read as pflag and getopt(3) read any flag, as gh and docker read it: after a flag that takes a value it is that value, and a later `--help=false` turns it off (`TestHelpIsReadAsAnyFlag`). **Help and a wrong line are answered before the environment or the mailbox is read** (the root's `PersistentPreRunE`, which cobra runs after both; each command's own values are checked in its argument check, `checked`). `-h` does the same, as in docker: it is in no help, and says on stderr that `--help` is the flag (`MarkShorthandDeprecated`, and the same line from the script).
- **A command line that is wrong runs nothing and exits 2** (`usageError`): a bare group, a command that is not one, a bad flag, the wrong number of arguments, with a `usage_error` line on stderr. A command's `help` is not help when the command takes arguments (an alias may be named `help`).
- **Flags are written with two dashes** in the help, the README, error text and dromas.dev's `llms.txt`, and may come anywhere after the command. 🛑 **No flag has a shorthand, and `-h` is never given a meaning** (`command` in `cmd/dromas/main.go` has why): `TestFlagsAreWrittenWithTwoDashes` holds every command to both.

### Names and modules

- **The name** is written Dromas in the README's prose, and `dromas` in every command, label, path and format.
- **The words:** a *message* is what is sent, its *envelope* the signed wrapper and its *body* the content; it lands in a *mailbox*, whose folders are `inbox/`, `outbox/`, `held/`, `refused/` and `sent/`; a line's own words are its `detail`. Never "mail" or "box", in prose, help, a line, a code or a name (#522): `TestTheClientSaysMessageAndMailbox` holds the help and every line's names, `TestTheWireSaysMessageAndMailbox` the API's codes, titles and quotas. The names stored in a mailbox's `state` file keep their spelling.
- **Module path:** `github.com/dromas-dev/dromas-client`. Installing must never depend on the dromas.dev server.
- **`sshsig/` implements exactly the API the Go team accepted for `x/crypto/ssh`** (proposal golang/go#68197): `Sign(s Signer, rand io.Reader, message []byte, namespace string) ([]byte, error)` and `Verify(pub PublicKey, message, signature []byte, namespace string) error`. `Verify` accepts sha256 and sha512, and reads `reserved` as OpenSSH does (`TestReservedAsSSHKeygen`). When `x/crypto` ships it, check that its `Verify` does the same, then switch the import and delete ours. Its implementation, CL 659715, is unmerged at x/crypto v0.58.0.
